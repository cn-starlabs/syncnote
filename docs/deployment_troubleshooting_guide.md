# SyncNote Deployment & Network Troubleshooting Guide

This guide documents the root causes, diagnostic steps, and permanent solutions discovered while deploying and running **SyncNote** (a Leptos 0.8 SSR + WASM Rust web application) on a Raspberry Pi server behind Cloudflare and Nginx.

---

## 1. Cloudflare Edge Cache Desynchronization (`LinkError`)

### Symptoms
* Some PCs/browsers loaded the app completely normally, while others had broken functionality.
* When clicking on notes in the left sidebar menu on affected machines:
  - The entire page reloaded instead of performing smooth SPA client-side navigation.
  - No background fetch request was made to `/api/note/get`.
  - The rendered Markdown preview was displayed (via SSR), but the raw source `<textarea>` editor was completely missing or empty.
* The browser DevTools Console showed:
  ```text
  Uncaught (in promise) LinkError: WebAssembly.instantiate():
  Import #0 "./syncnote_bg.js" "__wbindgen_object_drop_ref": function import requires a callable
  ```

---

### Root Cause
Rust web frameworks using `wasm-bindgen` compile the frontend into two tightly coupled artifacts in `/pkg/`:
1. `syncnote.wasm` — The binary WebAssembly containing the application logic.
2. `syncnote.js` — The JavaScript glue code generated by `wasm-bindgen` that exports functions and bridges DOM/browser APIs into the WebAssembly instance.

Every time the project is recompiled, `wasm-bindgen` generates unique internal function indices and import/export bindings between the `.js` and `.wasm` files. They **must always be loaded as an exact matching pair**.

#### Why Cloudflare Caused the Mismatch
Inspecting HTTP response headers from the production domain revealed:

| File | Response Header | Cloudflare Cache Status | Result |
|---|---|---|---|
| `/pkg/syncnote.js` | `cache-control: max-age=14400` | `cf-cache-status: HIT` | **Stale/Old JS served from edge cache** |
| `/pkg/syncnote.wasm` | *(No cache-control header)* | `cf-cache-status: DYNAMIC` | **Fresh/New WASM fetched from Pi** |

Cloudflare automatically caches static file extensions like `.js` by default (for 4 hours), but treats `.wasm` as `DYNAMIC` (not cached) unless a specific page rule is set.

As a result:
* Client browsers downloaded the **new** `syncnote.wasm` together with an **outdated** `syncnote.js`.
* When the browser executed `WebAssembly.instantiate()`, the imported function signatures did not match, throwing `LinkError`.
* Because WebAssembly crashed before hydration finished, client-side routing and reactive bindings never mounted. Clicking `<A href="...">` links triggered standard HTML fallback navigation (full page reloads), and reactive DOM elements like the note editor textarea failed to render.

---

### Solutions

#### Immediate Fix: Purge Cloudflare Cache
1. Open the [Cloudflare Dashboard](https://dash.cloudflare.com/).
2. Select your domain (`apich.top`) and navigate to **Caching** -> **Configuration**.
3. Click **Purge Everything** (or Purge URL: `https://note.apich.top/pkg/syncnote.js`).

#### Permanent Fix A: Nginx Header Configuration (Recommended)
Add a dedicated location block for `/pkg/` in your Nginx configuration so that neither Cloudflare nor downstream browser caches hold stale assets across deployments:

```nginx
# Nginx site configuration
location /pkg/ {
    proxy_pass http://127.0.0.1:7777; # your backend port
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;

    # Prevent Cloudflare and browsers from serving mismatched JS/WASM
    add_header Cache-Control "no-cache, no-store, must-revalidate, proxy-revalidate" always;
    add_header Pragma "no-cache" always;
    expires 0;
}
```

#### Permanent Fix B: Cloudflare Cache Rule
In Cloudflare:
1. Go to **Rules** -> **Cache Rules** (or **Page Rules**).
2. Create a rule matching:
   - URI Path starts with: `/pkg/`
3. Action:
   - **Cache Level**: **Bypass Cache**

## 2. Raspberry Pi IPv6 Precedence & Connection Timeouts

### Symptoms
* Outgoing connections from the Raspberry Pi server (such as downloading packages via `cargo`, cloning git repositories, updating APT packages, or connecting to external SMTP/APIs) hung indefinitely or failed with connection timeouts.
* Incoming requests or reverse-proxy routing occasionally stalled or failed to connect upstream.
* Disabling IPv6 immediately resolved the issues and made network traffic fast and reliable.

---

### Why Linux / Raspberry Pi OS Prefers IPv6 First

By default, Linux and Raspberry Pi OS implement **RFC 6724** (*Default Address Selection for Internet Protocol version 6*). Under this standard, the system resolver (`getaddrinfo`):

1. Queries DNS for both **AAAA (IPv6)** and **A (IPv4)** records.
2. If both records exist, the standard sorting policy assigns IPv6 addresses a higher precedence (Scope 14 vs Scope 4) and returns IPv6 first.
3. Applications attempting to connect will try the IPv6 address first before falling back to IPv4.

#### Why It Breaks in Real-World Home/Pi Setups
In many home router and ISP configurations:
* The ISP or local router assigns or advertises an IPv6 prefix via SLAAC or DHCPv6.
* However, the ISP lacks end-to-end IPv6 routing, the router's IPv6 firewall blocks outbound/inbound traffic, or MTU / Path MTU Discovery (PMTUD) issues cause IPv6 packets to be dropped silently without sending ICMPv6 "Packet Too Big" responses.
* When the Pi tries to connect via IPv6:
  - It sends TCP SYN packets to the IPv6 address.
  - No response or RST arrives.
  - The connection hangs until the operating system's TCP timeout expires (often 75 to 120+ seconds) before falling back to IPv4.

---

### How to Disable IPv6 or Prefer IPv4 on Raspberry Pi OS / Debian

#### Method 1: Kernel Sysctl (Cleanest & Recommended)
Create `/etc/sysctl.d/99-disable-ipv6.conf`:

```ini
net.ipv6.conf.all.disable_ipv6 = 1
net.ipv6.conf.default.disable_ipv6 = 1
net.ipv6.conf.lo.disable_ipv6 = 1
```

Apply with:
```bash
sudo sysctl --system
```

Verify IPv6 is disabled:
```bash
cat /proc/sys/net/ipv6/conf/all/disable_ipv6
# Returns: 1
```

#### Method 2: Prefer IPv4 Without Completely Disabling IPv6 (Alternative via `/etc/gai.conf`)
If you want to keep IPv6 active on your network but ensure the system resolver always tries IPv4 first:
Edit `/etc/gai.conf`:
```ini
# Change this:
#precedence ::ffff:0:0/96  100

# To this (uncomment):
precedence ::ffff:0:0/96  100
```
This raises IPv4-mapped IPv6 addresses above native IPv6, ensuring the resolver prefers IPv4 while keeping IPv6 capabilities available.

## 3. Summary Quick Reference

| Issue | Root Cause | Solution |
|---|---|---|
| **`LinkError: ... function import requires a callable`** | Cloudflare cached stale `syncnote.js` while serving new `syncnote.wasm`. | Purge Cloudflare cache; set `Cache-Control: no-cache` on `/pkg/`. |
| **Page reloads on note click; note source missing** | WebAssembly crashed during hydration due to mismatched JS/WASM assets. | Fix Cloudflare caching; clear browser cache (`Ctrl+Shift+R`). |
| **Pi server network hanging / timeouts** | RFC 6724 prefers IPv6, but local ISP/router has broken/blocked IPv6 routing. | Set `net.ipv6.conf.all.disable_ipv6 = 1` in `/etc/sysctl.d/99-disable-ipv6.conf` or prefer IPv4 in `/etc/gai.conf`. |
